# Рефлексия по практике 4

Я взял небольшую задачу с чётким поведением: отписка и просмотр подписчиков. Сначала закрепил контракт в `docs/requirements.md`, затем проверил фичу A. Фичу B делал в отдельном Git worktree: три новых теста сначала обнаружили отсутствие метода, после реализации прошли вместе с пятью прежними тестами. Fast-forward объединение сохранило последовательность работы видимой в истории коммитов.

`AGENTS.md` полезен тем, что задаёт агенту границы проекта и обязательные проверки. Skill `notify-tdd` даёт короткую команду для проверки одной фичи, а MCP `run_checks` позволяет агенту запускать тот же проверенный сценарий через инструмент. Hook после правки возвращает результат тестов прямо в ответ инструмента, поэтому ошибку можно заметить до следующего шага.

Сложнее всего оказалась настройка локального OpenCode: исходный контекст Ollama на 4096 токенов был меньше служебного запроса OpenCode примерно на 7370 токенов. Для этого я создал алиас `notify-agent` с контекстом 8192 из уже установленной Qwen3 4B, без повторной загрузки весов. Отдельная проверка MCP помогла отличить ошибки модели от ошибок инструмента: корректный `suite=all` прошёл, неверный `suite=wrong` вернул `isError=true` и понятный текст ошибки.

В длинном агентном сеансе локальная модель даже с увеличенным контекстом отвечала некорректным текстом. Поэтому для проверки реальных вызовов `read`, `skill`, MCP и hook я выбрал доступную бесплатную модель OpenCode. В этой конфигурации все четыре механизма сработали, а результат сохранён в `evidence/`.

При повторной проверке я заметил, что первый показанный hook запускался после правки документации. Я повторил агентный цикл на коде фичи A: агент прочитал требования и стиль, вынес общую проверку имени в приватный метод и получил зелёные результаты hook, skill и MCP.
