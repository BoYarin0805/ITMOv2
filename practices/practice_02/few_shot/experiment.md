# Few-shot

- Артефакт Практики 1: [product_management.md](../../practice_01/product_management.md#контракт-черновика-для-проверки).
- Что хотим улучшить: правило «каждый риск содержит файл, строку и наблюдение» допускает общие советы и выдачу ожидаемого поведения за уже проверенный факт.
- Вход: [TRAINING_PR.diff](../../practice_01/TRAINING_PR.diff), прежние [acceptance criteria](../../practice_01/product_management.md#user-stories-и-acceptance-criteria).

## Примеры

### Хороший результат

`app/api.py:10` — `payload["diff"]` обращается к ключу без проверки. При `{}` возникает `KeyError`. Проверка будущего контракта: `POST /api/reviews` с `{}` → 4xx с указанием `diff`, 0 вызовов LLM. Первые два утверждения следуют из diff; ответ 4xx — требование к будущему прототипу.

### Плохой результат

«API может работать плохо. Добавьте обработку ошибок и тесты; теперь пустой запрос возвращает 400». Нет ссылки и конкретного входа; `400` выдан за установленный факт, хотя приложения для запуска нет.

## Запрос

> Используй два примера выше как образцы качества. По `TRAINING_PR.diff` предложи критерий для замечания в будущем черновике ревью: файл и строка новой версии, видимое наблюдение, условное следствие, вход проверки и ожидаемый результат. Различай факт diff и требование к будущему сервису. Не утверждай, что тест запущен. Дай один хороший и один плохой пример для `product_management.md`.

## Что получили

Хороший пример привязан к `app/api.py:10`, пустому JSON и наблюдаемому результату. Плохой показывает две ошибки: совет без доказательства и придуманный статус текущего API. Это позволило сделать критерий оценки ответа конкретным: все показанные риски должны иметь место и проверку; статус проверки явно «предложено».
