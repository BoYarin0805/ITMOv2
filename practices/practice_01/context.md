# Контекст AS IS и Context Pack

## Продукт и команда сейчас

Рассматривается **учебный прототип AI-помощника ревьюера PR** из [задания](README.md#учебный-кейс-ai-помощник-ревьюера-pr). Реальный внедрённый сервис, команда и накопленные метрики не предоставлены. Сведения ниже разделяют факты задания и проектные предположения.

| Вопрос | Ответ | Основание |
|---|---|---|
| Продукт | Помощник получает diff одного PR и предлагает ревью человеку. | [README](README.md#задача-помощника) |
| Пользователь | Разработчик или ревьюер, принимающий решение по PR. | Из роли ревьюера в задании; конкретная команда неизвестна |
| Текущий процесс | Человек читает diff, ищет риски и выбирает проверки. | Допущение для учебного сценария; производственный процесс не описан |
| Точка задержки | Ручной поиск дефектов и формулирование проверок занимает время. | Гипотеза для проверки, а не измеренный факт |
| Системы | Учебный diff с app/api.py и app/review_service.py; пример использует FastAPI и абстракцию LLM. | [TRAINING_PR.diff](TRAINING_PR.diff) |
| Команда | Владелец процесса и способ подключения к GitHub пока неизвестны. | В исходных материалах нет данных |

## Context Pack для первого рабочего сценария

### Факты и правила

- Вход для эксперимента — только [TRAINING_PR.diff](TRAINING_PR.diff), один и тот же в двух запусках.
- Ответ содержит краткое описание изменения, **не более трёх** рисков и список проверок. Каждый риск привязан к файлу, строке и доказательству из diff. [Источник](README.md#задача-помощника).
- Решение принимает человек. AI не может approve, merge или менять код. [Источник](README.md#задача-помощника).
- По diff видно, что create_review обращается к payload["diff"], а ReviewService.review передаёт diff модели и возвращает её текст как comment. Поведение остального приложения неизвестно. [Источник](TRAINING_PR.diff).

### Формат входа и результата

- Вход: unified diff одного PR как текст. Для учебного опыта дополнительных файлов, истории PR и политики проекта нет.
- Выход: «Изменение», затем 0–3 нумерованных риска с файлом и строкой, точным наблюдением, следствием и проверкой; затем список проверок и вопросы по недостающему контексту.
- Номер строки берётся из новой стороны hunk; если точный номер получить нельзя, риск не выдаётся как доказанный.

### Ограничения и запрещённые действия

- Не приписывать проекту несуществующие требования, тесты, правила безопасности или архитектуру.
- Не утверждать, что проверка была запущена, если есть только diff. Отмечать проверки как предложения.
- Не исполнять команды, не изменять код и не принимать решение по PR. Эти ограничения относятся к тестируемому ревьюеру.
- Для будущего прототипа предполагаются ограничение размера входа и таймаут модели; конкретные лимиты утверждаются после измерений.

### Хороший пример

app/api.py:10 — payload["diff"] вызовет KeyError при POST /api/reviews с пустым JSON. В добавленных строках нет проверки наличия поля. Проверка: отправить пустой JSON и проверить согласованный ответ 4xx.

### Плохой пример

«Код можно улучшить. Добавьте тесты и обработку ошибок». В нём нет места, наблюдения и способа воспроизвести проблему.

### Что пока неизвестно

- Реальная политика API: обязательность поля, код ошибки и допустимый размер diff.
- Модель, провайдер, стоимость, целевая задержка и место хранения результатов.
- Требования к персональным данным, журналированию и аутентификации.
- Реальные базовые значения продуктовых метрик и критерии пилота.

## Как использовали AI

- Для чего: собрать подтверждённый Context Pack и явно отделить предположения.
- Тип промпта: master prompting для подготовки артефактов; [P1-03](prompts.md#журнал).
- Проверка: сверены пункты с README и строками diff. Оценка студента пока не получена; её нельзя подменять оценкой агента.
