# Независимая проверка результата

Дата: 29 октября 2026. Проверка проведена в отдельном контексте от реализации.
Прочитаны правила проекта, согласованные спецификации OpenSpec и избранного,
`forecast.py`, `server.py`, `static/app.js`, `favorites.js`, `scene.js`, HTML/CSS,
автоматические тесты. Продуктовый код при ревью не изменялся.

## Проверки и результат

Повторно выполнен `sh scripts/check.sh`: **29 тестов Python и 10 JavaScript — PASS**.
Проверки покрывают ошибки провайдера, координаты, независимый маршрут прогноза,
полуночную границу, DST, неизвестный целый WMO-код, повреждённое хранилище,
дедупликацию по координатам, лимит и сеансовую работу при отказе записи.

Отдельно прочитан итоговый результат браузерного набора `evidence/browser-results.json`:
8 сценариев PASS (запуск 2026-10-28T22:31:32Z), без flaky/skipped/unexpected. Это сценарии с управляемыми
API-ответами, они не выдаются за измерение реальной погоды.

## Сверка требований с реализацией

| Требование | Проверенный механизм / доказательство |
| --- | --- |
| Ровно 24 будущих полных часа | Отбор по Unix-времени и проверка шага 3600; тесты точного часа и полуночи |
| Местное время независимо от устройства | `zoneinfo`, локальные ISO-строки с offset; тест Europe/Berlin с повторным часом, браузер с другой зоной |
| Неизвестный целый код не вызывает ложную ошибку источника | Число сохраняется, состояние отображается как unknown; отдельный тест |
| Прогноз не меняет реальные числа | Отдельный selectedHour, браузерный сценарий прогноз → Сейчас → демо |
| Смена города сбрасывает будущий предпросмотр | selectedHour очищается в пути выбора; браузерная проверка |
| Устаревший ответ не заменяет новый | Отдельные счётчики weather/forecast/search; задержанный ответ прогноза в браузерном сценарии |
| Отказ прогноза сохраняет текущую карточку | Независимые API и UI-ошибки; HTTP и браузерная проверка восстановления |
| Избранное не зависит от погоды | Отдельное selectedLocation, дополнительная независимая проверка с заблокированным ответом weather |
| Повреждение localStorage не ломает погоду | Нормализация, фильтрация отдельных записей, отсутствие записи при чтении; unit-тесты |
| Удаление не меняет открытый город | Удаляется только запись store, фокус возвращается на добавление; браузерный сценарий |
| Отказ localStorage оставляет сеансовый список | Session-first изменение и явное предупреждение после неуспешного сохранения |
| Без HTML-инъекций из имени | Имена и результаты выводятся через textContent/Option, не innerHTML |

## Дополнительный независимый браузерный эксперимент

Для проверки спорного сценария ответ `/api/weather` намеренно задержан. После
получения `/api/cities` добавление уже доступно: число записей избранного стало 1,
пока текущая карточка оставалась скрыта. Затем ответ разрешён, карточка загрузилась.
Это подтверждает добавление до завершения погодного запроса, а не только после него.

С `prefers-reduced-motion: reduce` проверено состояние видео до и после смены
источника: `paused=true`. Погодные числа и управление остаются доступны.
Тестовый сервер остановлен; временные данные эксперимента ограничены папкой проекта.

## Замечания и ограничения

После исправлений подтверждённых оставшихся блокирующих дефектов по согласованным требованиям нет.
Три уточнения до кода из `forecast-before.md` учтены: различимый UTC-offset,
unknown для нового целого WMO-кода и сброс будущего часа при смене города.

В исходном браузерном сценарии с названием «add before weather response» сначала
ожидалась текущая карточка. Замечание о недостаточности такого доказательства
передано в основной контекст; добавлен постоянный сценарий с заблокированным ответом
погоды. Он входит в итоговые 8 PASS и подтверждает добавление до ответа сети.

В исходной версии поставленный тестовый Chromium возвращал для MP4 `MediaError`
code 4 / readyState 0. Это было реальным дефектом совместимости требуемых футажей,
а не успешным воспроизведением: работали только постеры. После замечания все шесть
роликов дополнены WebM/VP9, WebM выбран первым, MP4 оставлен запасным вариантом.
Итоговый браузерный сценарий проверяет readyState >= 2, продвижение currentTime
более 0.15 секунды и остановку времени после нажатия паузы. Он прошёл в свежем
запуске после конвертации, поэтому найденная проблема считается исправленной.
Загрузка метаданных дополнительно соблюдает выбранную паузу/reduced motion.
В `static/media/playback-check.json` отдельно проверены все шесть WebM-файлов:
для каждого readyState=4, продвижение currentTime более 0.8 секунды,
размер кадра 960×540 и отсутствие mediaError; общий результат PASS.

Остаточные пределы: тесты не подменяют оценку субъективного оформления, а реальный
погодный источник может быть временно недоступен. Для такого отказа есть явные
ошибки; фиктивные числа не подставляются.
